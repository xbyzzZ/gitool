# Gitool 远程设置交互修复设计

## 背景

提交信息区右上角的三个点表示远程设置。当前实现只支持修改已有远程 URL；仓库没有远程时，按钮仍可点击，客户端先进入请求中状态，宿主随后返回“当前仓库没有可修改的远程”，造成按钮闪烁和无效操作。

## 目标

- 无远程仓库点击远程设置时，直接添加名为 `origin` 的远程。
- 已有远程仓库继续使用现有的选择和修改 URL 流程。
- 用户取消输入或确认时安静结束，不写入错误状态。
- 所有远程配置写入继续遵守工作区信任、仓库版本和操作锁约束。

## 非目标

- 不提供自定义新远程名称；新增远程固定使用 Git 默认惯例 `origin`。
- 不在本次实现删除、重命名远程。
- 不改变拉取、推送和上游分支策略。

## 交互设计

点击远程设置后，宿主读取当前仓库的远程列表：

- 列表为空：显示“Gitool：添加远程 origin”输入框，要求输入完整 URL。用户确认后再执行写入。
- 列表非空：保留“选择现有远程 → 输入新 URL → 确认修改”的现有流程。
- 用户取消任一输入框或确认框：直接结束请求，不显示错误。
- Git 校验或写入失败：通过现有操作反馈区显示明确错误。

按钮继续使用现有请求确认机制。无远程时不再抛出“没有可修改的远程”，因此不会出现失败状态引发的禁用、恢复闪烁。

## 实现边界

### RemoteService

新增 `add(repositoryRoot, name, url)`：

1. 校验名称和 URL 非空。
2. 确认同名远程不存在。
3. 执行 `git remote add -- <name> <url>`。
4. 使用机器可解析输出重新读取 URL，按原始值校验写入结果。
5. 校验失败时移除本次刚创建的远程，避免留下半完成配置；清理失败时同时报告写入和清理错误。
6. 返回时对 URL 中的凭据脱敏。

### RepositoryWriteCoordinator 与 RepositoryService

新增添加远程请求，并复用现有 `runValidatedWrite` 与 `remote` 操作状态。写入前执行工作区信任、仓库版本、真实快照和操作锁检查。

### GitoolViewProvider

将现有远程设置处理分为两条路径：

- 没有远程时收集并确认 `origin` URL，调用添加远程服务，随后刷新仓库。
- 有远程时调用现有修改流程。

Webview 消息类型和按钮事件不变，避免引入额外客户端状态。

## 错误与安全

- 空白 URL 在输入阶段和服务层双重拒绝。
- 同名远程在写入前拒绝，避免覆盖已有配置。
- URL 含凭据时，确认信息、返回结果和错误上下文只显示脱敏值。
- 使用参数数组调用 Git，不经过 shell 拼接。
- 写入后读取值与请求值不一致时回滚新增远程并报告校验失败，不静默成功。

## 测试

- RemoteService 集成测试：添加 `origin`、拒绝空 URL、拒绝同名远程、写后校验。
- RepositoryWriteCoordinator 单元测试：添加远程经过写校验与 `remote` 操作状态。
- GitoolViewProvider 单元测试：无远程时输入并添加 `origin`、取消时不写入、已有远程仍走修改路径。
- 运行类型检查、lint、全量测试、扩展构建和 VSIX 打包。
