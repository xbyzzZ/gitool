# Gitool 文件提交插件设计

## 1. 目标

创建一个桌面版 VS Code 插件，在独立侧边栏中提供接近 PyCharm Commit 工具窗口的按文件提交体验：

- 支持在多仓库工作区中选择单个仓库。
- 支持按文件选择本次提交范围。
- 已跟踪变更首次默认选中，未跟踪文件首次默认不选中。
- 支持将未跟踪文件手动移入系统废纸篓。
- 支持“提交”和“提交并推送”。
- 无上游分支时可选择已有远程并建立同名上游分支。
- 支持修改已有远程的 URL。
- 严格保留未选文件及其既有暂存状态。

首版只支持文件粒度，不支持同一文件内部按代码块提交。

## 2. 产品边界

### 2.1 支持范围

- 桌面版 VS Code。
- macOS、Windows 和 Linux。
- 本地工作区，以及运行在 SSH、WSL 或 Dev Container 扩展主机中的仓库。
- 单个 VS Code 工作区内的多个 Git 仓库，但一次只操作用户当前选择的一个仓库。
- 已修改、已删除、已重命名、未跟踪和存在暂存/未暂存双重状态的文件。

### 2.2 不支持范围

- 浏览器版 VS Code。
- 跨仓库一次性提交或推送。
- 文件内部按代码块提交。
- 新增、重命名或删除远程。
- 自动解决合并或变基冲突。
- 自动回滚已经成功创建的本地提交。

### 2.3 精确提交语义

- 未选文件不会进入本次提交，其工作区内容和暂存状态保持不变。
- 已选文件按当前工作区的完整文件内容提交。
- 同一已选文件原先的暂存与未暂存区分会被本次提交消耗。
- 同一未选文件即使同时存在暂存和未暂存修改，也不会被本次提交触碰。

## 3. 技术方案

采用混合架构：

- Webview 侧边栏负责接近 PyCharm 的勾选列表、提交信息输入框和操作按钮。
- VS Code 内置 Git 扩展 API 负责仓库发现、状态事件、分支、远程和认证推送。
- 本机 Git 进程负责按路径提交和修改已有远程 URL。
- VS Code 文件系统 API 负责将未跟踪文件移入系统废纸篓。

选择该方案的原因：

- Webview 能在一个连续界面中承载仓库选择、文件勾选、提交信息和双操作按钮。
- 内置 Git API 的推送可以复用 VS Code 现有的 HTTPS 或 SSH 认证能力。
- Git 的按路径提交语义可以精确忽略其他路径已经暂存的内容。
- Git 写操作留在扩展主机中，Webview 不直接接触进程、文件系统或凭据。

## 4. 界面设计

### 4.1 仓库栏

侧边栏顶部显示：

- 当前仓库名称和根目录。
- 当前分支。
- 当前上游状态。
- 仓库选择器。

仓库切换后，文件列表、选择状态、提交信息和远程信息均切换到对应仓库上下文。一次写操作只能作用于一个仓库。

### 4.2 文件列表

文件分为两个分组：

1. 已跟踪变更。
2. 未跟踪文件。

已跟踪变更首次出现时默认选中。未跟踪文件首次出现时默认不选中，刷新不能将其自动选中。

每个文件行显示：

- 复选框。
- 修改、删除、重命名、未跟踪或双状态图标。
- 仓库相对路径。
- 暂存与未暂存双重状态标记。

点击文件打开 VS Code diff。未跟踪文件打开普通编辑器或新文件 diff。

未跟踪目录必须展开为具体文件，不能把整个目录作为单个提交项。每个分组提供全选和全不选，顶部显示已选择文件数量。

冲突文件显示错误状态且不可选。仓库存在未解决冲突时，整个提交操作禁用。

### 4.3 提交区

侧边栏底部固定显示：

- 多行提交信息输入框。
- “提交”按钮。
- “提交并推送”主按钮。
- 操作状态和错误摘要。

以下任一条件成立时，提交按钮禁用：

- 提交信息为空或只包含空白。
- 没有选择文件。
- 仓库存在冲突。
- 当前仓库正在执行写操作。
- 工作区未受信任。
- 当前状态快照已过期且尚未刷新。

游离 `HEAD` 时允许本地提交，但禁用“提交并推送”，并提示用户先创建或切换分支。

### 4.4 未跟踪文件舍弃

未跟踪文件的行内菜单和右键菜单提供“移入废纸篓”。

执行前必须：

- 展示将被处理的具体文件清单。
- 要求用户二次确认。
- 明确说明文件将移入系统废纸篓，可从系统废纸篓恢复。

操作按文件逐项执行。部分文件失败时必须逐项报告，不能把部分成功描述为全部成功。

### 4.5 远程 URL 修改

更多菜单提供“修改远程 URL”：

- 只能选择已有远程。
- 显示远程名称和当前 URL。
- 输入新 URL 后二次确认。
- 写入后重新读取 Git 配置并比对。
- 只有重新读取值与输入一致时才报告成功。

首版不提供新增、重命名或删除远程。

## 5. 状态与选择模型

每个仓库拥有独立状态：

- 仓库标识和根目录。
- 当前分支、上游和远程列表。
- 标准化后的文件变更。
- 文件选择集合。
- 提交信息。
- 状态版本号。
- 当前写操作状态。

状态刷新规则：

- 同一路径的暂存和未暂存变化合并成一个文件项。
- 仍存在的文件保留用户最近一次人工选择。
- 新出现的已跟踪变更默认选中。
- 新出现的未跟踪文件默认不选中。
- 已消失的文件从选择集合移除。
- Webview 发起写操作时必须携带状态版本号。
- 扩展主机发现版本号过期时拒绝写操作并要求刷新。

## 6. 提交流程

### 6.1 提交前复核

扩展主机在执行前重新读取仓库状态，不信任 Webview 的旧数据，并校验：

- 提交信息有效。
- 至少选择一个文件。
- 所选路径仍对应可提交变更。
- 仓库不存在冲突。
- 当前仓库没有其他写操作。
- 工作区受信任。

所有 Git 调用必须使用进程参数数组，不经过 Shell。路径参数必须放在 `--` 之后，避免文件名被解释为选项。

### 6.2 按路径提交

流程为：

1. 记录所选路径及其中原本为未跟踪状态的路径。
2. 对所选未跟踪文件执行 `intent-to-add`，使其进入 Git 按路径提交的识别范围。
3. 使用 `git commit --only` 提交全部所选路径的当前完整内容。
4. 提交信息通过权限受限的临时文件传递。
5. 读取新的提交哈希和实际文件清单。
6. 将实际提交范围与预期路径集合进行规范化比对。
7. 刷新仓库状态。

该流程不会把其他路径已经暂存的内容带入提交。

### 6.3 提交失败恢复

若 `intent-to-add` 或提交失败：

- 撤销本次为原未跟踪文件增加的索引登记。
- 不执行 `reset --hard`、`checkout` 或任何会修改工作区文件内容的命令。
- 保留提交信息和选择状态。
- 展示根因明确的错误信息，并提供脱敏后的详细输出。

若提交已经创建，但提交范围核对失败：

- 标记为严重错误。
- 立即停止后续推送。
- 不自动重写或回滚提交。
- 展示新提交哈希和实际范围，要求用户人工处理。

## 7. 推送流程

### 7.1 已有上游

“提交并推送”在本地提交成功后，调用 VS Code 内置 Git API 推送到当前分支上游。

### 7.2 无上游

若当前分支没有上游：

1. 展示已有远程列表。
2. 用户选择一个远程。
3. 将当前分支推送到同名远程分支。
4. 设置该远程分支为当前分支上游。

不自动新增远程。

### 7.3 推送失败

推送失败时：

- 不撤销已经成功的本地提交。
- 明确显示“本地提交已成功，推送失败”。
- 显示本地提交哈希。
- 提供“重试推送”。
- 不重复创建提交。

## 8. 并发、安全与错误处理

- 每个仓库使用独立写操作互斥队列。
- 同一仓库执行写操作时禁用其他提交、舍弃和远程修改动作。
- Webview 消息必须经过运行时结构校验，未知消息和非法字段直接拒绝。
- Webview 使用严格内容安全策略，不允许任意脚本和网络资源。
- Git 输出、远程 URL 和错误信息必须遮蔽 URL 用户信息、密码和令牌。
- 临时提交信息文件使用仅当前用户可读写的权限，并在操作结束后删除。
- 工作区未受信任时仅允许查看状态。
- 不使用无意义异常捕获、静默失败或默认值掩盖错误。
- 所有失败必须保留明确的操作阶段、Git 退出码和可理解的中文说明。

## 9. 模块划分

### 9.1 扩展入口

负责激活插件、获取内置 Git API、注册侧边栏、命令和工作区信任监听。

### 9.2 仓库服务

负责仓库发现、仓库切换、状态订阅、状态版本号和标准化仓库视图模型。

### 9.3 状态服务

负责读取和解析 Git 状态，合并同一路径的暂存与未暂存状态，识别未跟踪、重命名和冲突。

### 9.4 选择服务

负责按仓库保存选择集合，实现默认选择和刷新保留规则。

### 9.5 提交服务

负责提交前复核、按路径提交、未跟踪文件临时登记、失败恢复和提交范围核对。

### 9.6 推送服务

负责已有上游推送、无上游远程选择、建立上游和失败重试。

### 9.7 远程服务

负责读取已有远程、修改 URL、写后复核和敏感信息遮蔽。

### 9.8 废纸篓服务

负责二次确认和逐文件移入系统废纸篓。

### 9.9 Webview 提供器

负责渲染、主题适配、无障碍属性、状态展示和声明式消息发送，不直接执行 Git 或文件系统操作。

## 10. 测试策略

### 10.1 单元测试

覆盖：

- Git 状态解析。
- 同一路径双状态合并。
- 已跟踪与未跟踪文件的默认选择。
- 刷新后的人工选择保留。
- 冲突状态禁用。
- 状态版本过期拒绝。
- Webview 消息校验。
- 远程 URL 和错误输出脱敏。

### 10.2 真实 Git 集成测试

测试使用临时真实仓库和本地裸远程，覆盖：

- 只提交勾选的已跟踪文件。
- 未选文件的暂存内容保持不变。
- 选中的未跟踪文件成功提交。
- 未选中的未跟踪文件仍保持未跟踪。
- 已删除和已重命名文件。
- 包含空格、中文和以短横线开头的文件名。
- 提交钩子拒绝时恢复原未跟踪状态。
- 无上游分支首次推送并建立上游。
- 已有上游分支后续推送。
- 修改远程 URL 后重新读取一致。

### 10.3 VS Code 扩展测试

覆盖：

- 插件激活。
- 多仓库发现和切换。
- Webview 与扩展主机消息往返。
- 工作区信任限制。
- Git 扩展不可用时的明确提示。

### 10.4 交付验证

交付前必须完成：

- TypeScript 类型检查。
- 代码规范检查。
- 全部单元测试和集成测试。
- 生产构建。
- VSIX 打包。
- 在 Extension Development Host 中执行一次真实交互验收。

## 11. 验收标准

- 独立侧边栏可以选择工作区中的单个 Git 仓库。
- 已跟踪变更首次默认选中。
- 未跟踪文件首次和刷新后默认不被自动加入提交。
- 用户可以逐文件勾选本次提交范围。
- 用户可以二次确认后把未跟踪文件移入系统废纸篓。
- 提交只包含勾选文件。
- 未勾选文件及其暂存状态不受影响。
- 提供“提交”和“提交并推送”。
- 无上游时可以选择已有远程并建立同名上游。
- 推送失败不会掩盖本地提交成功，也不会重复创建提交。
- 用户可以修改已有远程 URL，并得到写后复核结果。
- 冲突、过期状态、未信任工作区和重复操作均被明确阻止。
- 日志和错误输出不泄露远程凭据。
- 交付源码、中文 README、自动化测试和可安装 VSIX。
